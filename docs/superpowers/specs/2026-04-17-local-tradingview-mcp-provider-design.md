# DEV-122 Local TradingView MCP Provider Wrapper Design

## Summary

Design a local-only provider wrapper that exposes TradingView chart context over HTTP for the existing AI Operating Layer. The wrapper will run on the same machine as TradingView Desktop and `tradingview-mcp`, call the MCP CLI in read-only mode, and normalize the result into the `/chart-context` contract the main backend already expects.

## Goals

- Turn the working local `tradingview-mcp` setup into a callable HTTP provider.
- Reuse the existing provider contract already consumed by:
  - `src/adapters/tradingview_chart_provider.py`
  - `src/services/chart_context_service.py`
- Keep the first version local-first and easy to debug with `curl`.
- Feed chart-aware context into the upgraded AI agents without changing the live trading path.
- Preserve graceful degradation when TradingView or MCP is unavailable.

## Non-Goals

- No direct integration with Railway in v1.
- No TradingView control or mutation actions in v1.
- No screenshots required in v1.
- No multi-chart or multi-pane aggregation in v1.
- No automatic provider tunneling or deployment in v1.
- No execution-time trade gating based on provider responses in v1.

## Existing Context

Three pieces are already in place:

1. The main backend already fetches chart context from a configurable `/chart-context` endpoint.
2. The AI Operating Layer already normalizes provider results and handles degraded chart context.
3. The local `tradingview-mcp` installation is now verified against a live TradingView Desktop chart.

The missing piece is a local service that translates MCP CLI output into the backend’s expected provider payload.

## Proposed System Shape

Add one new local service:

- `TradingViewMcpProvider`

The data path becomes:

1. TradingView Desktop runs locally with CDP enabled on port `9222`.
2. `tradingview-mcp` CLI reads the live chart via CDP.
3. The new local wrapper service calls the MCP CLI commands.
4. The wrapper combines and normalizes the results into one `/chart-context` response.
5. The existing backend provider adapter consumes that HTTP response unchanged.

This keeps the provider bridge separate from the main backend and makes local debugging straightforward.

## Runtime Placement

### First rollout

- runs only on the operator machine
- shares the same machine as:
  - TradingView Desktop
  - `tradingview-mcp`

### Later rollout

- can be exposed through a tunnel for Railway
- can later move to an always-on machine if TradingView Desktop is also moved there

## Recommended Implementation Stack

Use Python for the wrapper service.

Why:

- the consuming application is already Python-based
- the provider contract is already modeled on the Python side
- error handling and normalization can closely mirror backend expectations
- the wrapper can still call the Node CLI without duplicating MCP logic

## API Contract

Expose one endpoint:

- `GET /chart-context?symbol=<symbol>&timeframe=<timeframe>`

The first version should ignore symbol and timeframe switching requests and instead report the currently active chart state from TradingView. If the requested symbol/timeframe does not match the active chart, the response should still return the actual active chart and include a mismatch note in metadata or reason text.

Why:

- v1 is read-only only
- changing symbol or timeframe would cross into chart-control behavior
- the AI layer still benefits from truthful current chart context

## Required Response Shape

The wrapper should return:

```json
{
  "symbol": "VANTAGE:AUDUSD",
  "timeframe": "5m",
  "provider_timestamp": "2026-04-17T00:18:40Z",
  "pine_labels": [],
  "zones": [],
  "indicator_values": {}
}
```

Optional v1 fields:

- `screenshot_url`
- `metadata`

The response must always reflect the actual active chart, not the requested symbol/timeframe if they differ.

## Data Sources Inside the Wrapper

The wrapper should call these MCP CLI commands:

- `node src/cli/index.js status`
- `node src/cli/index.js quote`
- `node src/cli/index.js values`
- `node src/cli/index.js data lines`
- `node src/cli/index.js data labels`

These provide the first complete chart-awareness slice:

- active symbol and timeframe
- current quote snapshot
- study values
- Pine horizontal levels
- Pine labels carrying entries, stop loss, take profit, and setup tags

## Normalization Rules

### `symbol`

- source: `status.chart_symbol`

### `timeframe`

- source: `status.chart_resolution`
- normalize TradingView `"5"` to API `"5m"` for intraday numeric resolutions
- preserve higher-timeframe strings such as `D`, `W`, `M` as-is or with minimal explicit mapping

### `provider_timestamp`

- generated by the wrapper at response time in UTC ISO-8601 format

### `indicator_values`

- source: `values.studies`
- normalize into a dict keyed by study name
- preserve study output names and string/number values

Example:

```json
{
  "Moving Average Exponential": {
    "EMA": "0.71664"
  },
  "Institutional Liquidity Protocol [Pro]": {
    "Shapes": "0.00000"
  }
}
```

### `pine_labels`

- source: `data labels`
- flatten study labels into a list of artifacts
- include:
  - `type: "label"`
  - `source: "pine"`
  - `label`: text content
  - `price`
  - optional `study`

### `zones`

- source: `data lines`
- convert horizontal levels into normalized zone/level artifacts
- include:
  - `type: "horizontal_level"`
  - `source: "pine"`
  - `label`
  - `price`
  - optional `study`

If future line payloads include regions or boxes, they can continue to map into the same `zones` array.

## Error Handling

The wrapper should degrade cleanly in these cases:

- TradingView not running
- CDP unavailable
- MCP CLI command fails
- one MCP command succeeds but another returns malformed JSON
- active chart not fully loaded yet

Recommended response behavior:

- return HTTP `200` with a degraded payload for expected operational failures
- include:
  - actual or requested `symbol`
  - actual or requested `timeframe`
  - `reason`
  - empty `pine_labels`
  - empty `zones`
  - empty `indicator_values`
  - `provider_timestamp`

This matches the existing backend’s graceful degradation model better than surfacing transport-level failures for normal runtime problems.

## Process Model Inside the Wrapper

For each request:

1. run `status`
2. if `status` fails, return degraded payload immediately
3. run `quote`, `values`, `data lines`, and `data labels`
4. tolerate partial failures from the secondary commands
5. build the normalized response
6. return the combined payload

The wrapper should not fail the entire request just because one enrichment call fails, as long as `status` succeeds and the active chart is known.

## Logging and Observability

The wrapper should log:

- request start
- requested symbol/timeframe
- actual active symbol/timeframe
- per-command failures
- degraded reasons

Logs can stay simple in v1 and write to stdout.

## Local Debugging Workflow

The service should be easy to validate locally with:

```bash
curl "http://localhost:8765/chart-context?symbol=VANTAGE:AUDUSD&timeframe=5m"
```

The intended debug loop is:

1. launch TradingView with CDP
2. verify `tradingview-mcp` via CLI
3. run the local provider wrapper
4. verify the wrapper endpoint with `curl`
5. later point a local or tunneled backend at the wrapper

## Safety Rules

- wrapper is read-only only
- wrapper must never issue chart mutation commands
- wrapper must never send MCP UI commands
- wrapper should treat CLI output as untrusted input and parse defensively
- wrapper should avoid blocking indefinitely on CLI processes

## First Implementation Slice

Build:

- a small Python HTTP service
- one `GET /chart-context` route
- subprocess execution of the verified MCP CLI commands
- normalization into:
  - `provider_timestamp`
  - `pine_labels`
  - `zones`
  - `indicator_values`
- local stdout logging
- degraded payload handling

Do not build yet:

- public exposure
- tunneling automation
- screenshots
- symbol/timeframe switching
- multi-pane support
- TradingView control actions

## Rollout Plan

### Phase 1

- local-only provider wrapper
- local `curl` verification
- compare payload against backend normalization contract

### Phase 2

- connect upgraded post-trade debate agents to the local provider output
- run chart-aware agent evaluation in shadow mode

### Phase 3

- expose provider through a tunnel for Railway
- configure the backend provider endpoint to use the public tunnel URL

## Recommendation

Build the local wrapper first and feed it into the existing AI agent system before changing optimizer or alert architecture. The highest-leverage near-term win is making the existing agents chart-aware, not replacing them with MCP.
