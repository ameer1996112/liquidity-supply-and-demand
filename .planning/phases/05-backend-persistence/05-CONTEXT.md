## Phase Boundary

Deliver a self-sustaining backend: launchd plists for API + Worker on macOS, Redis pre-flight check, persistent log files, and an idempotent `start.sh fullstack` that never starts duplicate processes.

<code_context>
## Existing Code Insights

### Reusable Assets
- `start.sh` — existing full-stack launcher (source of truth for how services start)
- `venv/` Python virtualenv at project root (NOT `.venv`)
- `src/api.py` — FastAPI app entry point (`src.api:app`)
- `src/worker.py` — worker entry point (`src.worker`)
- Redis expected at `localhost:6379`

### Established Patterns
- Backend: `source venv/bin/activate && PYTHONPATH=$(pwd) python3 -m uvicorn src.api:app --host 0.0.0.0 --port 8000`
- Worker: `source venv/bin/activate && PYTHONPATH=$(pwd) python3 -m src.worker`
- Health check: `GET /health` → `{"status":"healthy","service":"api"}`

### Integration Points
- `start.sh` is the entrypoint — modify to add idempotency and launchd support
- Logs should go to `~/.tradeops/logs/` (create dir if needed)

</code_context>

<specifics>
## Specific Ideas

- launchd plist files generated by an `install-services.sh` script (not committed with hardcoded paths)
- PID file at `/tmp/tradeops-api.pid` and `/tmp/tradeops-worker.pid` for process tracking
- `start.sh` checks if port 8000 is occupied before launching

</specifics>

<deferred>
## Deferred Ideas

- pm2 support (macOS launchd is sufficient and has no Node.js dependency)
- Docker containerisation (out of scope)

</deferred>
